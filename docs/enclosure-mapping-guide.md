## Overview

The Drive Wipe Station uses an enclosure-based physical slot mapping system to correlate physical drive bays with Linux device paths. This replaces static `/dev/sdX` naming with stable hardware identifiers that survive SCSI bus resets and expander re-enumeration.

### Key Concepts

- **Master Slot Map**: A hardware inventory of all physical slot lanes, generated by scanning sysfs. Contains PCI controller addresses, slot types, expander SAS addresses, and hardware identifiers.
- **Enclosures**: Physical chassis/backplanes configured with templates, PCI controllers, and optional SAS expander addresses.
- **Templates**: Physical layout definitions (grid dimensions, traversal order, hybrid slots) independent of hardware.
- **Slot Mappings**: Per-slot hardware bindings that map a physical slot number to a specific device path via `/dev/disk/by-path/` entries.
- **Hybrid Slots**: Physical slots that support multiple interface types (e.g., SAS/SATA + NVMe in the same bay).

---

## Supported Slot Types

| Slot Type | Description | Hardware Identifier Format | sysfs Source |
|-----------|-------------|---------------------------|--------------|
| `sas_expander` | HBA + SAS expander topology | `phy-0:0:N` | `/sys/class/sas_phy` + `/dev/disk/by-path` |
| `sas_direct` | Direct HBA connection (no expander) | `phy-X:Y:Z` | `/dev/disk/by-path` (scsi pattern) |
| `motherboard_sata` | Onboard AHCI ports | `ataN` | `/dev/disk/by-path` + `/sys/class/ata_port` |
| `pcie_nvme` | U.2/U.3 hotplug bays | Slot folder name (e.g., `101`) | `/sys/bus/pci/slots/` |

## Configuration File

Enclosure configuration is stored in `config/bay_map.json`. The file has two main sections:

### Legacy Bay Map Format (bay-by-bay)

```json
{
  "layout_metadata": {
    "template_id": "dell_r320_4bay",
    "traversal_preset": "top_left_down_then_across",
    "custom_overrides": {}
  },
  "bays": {
    "bay0": {
      "role": "wipe",
      "locked": false,
      "type": "sas_sata",
      "label": "Work Bay A (Slot 0)",
      "by_path": "pci-0000:00:1f.2-ata-1",
      "display_number": "0"
    },
    "bay1": {
      "role": "os",
      "locked": true,
      "label": "OS Drive (Slot 1)",
      "by_path": "pci-0000:00:1f.2-ata-2",
      "display_number": "1"
    }
  }
}
```

### Enclosure-Based Format

```json
{
  "templates": [
    {
      "id": "dell_r440_10bay",
      "name": "Dell R440 10-Bay (2.5\")",
      "vendor": "Dell",
      "rows": 2,
      "cols": 5,
      "bay_count": 10,
      "slot_count": 10,
      "traversal_preset": "top_left_down_then_across",
      "hybrid_slots": [1, 5, 9]
    }
  ],
  "enclosures": {
    "enc_1": {
      "id": "enc_1",
      "name": "Front Bay Array",
      "template_id": "dell_r440_10bay",
      "pci_controller": "0000:af:00.0",
      "expander_sas_address": "0x500056b3059bdcff",
      "display_order": 0,
      "slots": {
        "0": {
          "physical_slot_number": 0,
          "label": "Bay 1",
          "role": "wipe",
          "locked": false,
          "mappings": {
            "sas_sata": {
              "slot_type": "sas_expander",
              "hardware_identifier": "phy-0:0:0",
              "auto_detected": true,
              "pci_controller": "0000:af:00.0",
              "expander_sas_address": "0x500056b3059bdcff"
            }
          }
        }
      }
    }
  }
}
```

### Schema Reference

#### Template Schema

| Field | Type | Required | Constraints |
|-------|------|----------|-------------|
| `id` | string | Yes | Lowercase, alphanumeric, hyphens, underscores |
| `name` | string | Yes | Human-readable name |
| `vendor` | string | No | Hardware vendor |
| `slot_count` | integer | Yes | 1-1000 |
| `bay_count` | integer | No | 1-128 (defaults to rows x cols) |
| `rows` | integer | No | 1-16 |
| `cols` | integer | No | 1-5 |
| `traversal_preset` | string | No | One of the 4 supported presets |
| `hybrid_slots` | array | No | Array of physical slot numbers (integers, max 128) |
| `skip_positions` | array | No | Array of `{row, col}` objects (max 100) |
| `default_role` | string | No | `wipe`, `os`, or `reserved` |

#### Enclosure Schema

| Field | Type | Required | Constraints |
|-------|------|----------|-------------|
| `id` | string | Yes | Unique enclosure identifier |
| `name` | string | Yes | Min 2 characters |
| `template_id` | string | Yes | References a template |
| `pci_controller` | string | Yes | PCI address format `XXXX:XX:XX.X` |
| `expander_sas_address` | string\|null | No | SAS WWN format `0x...` (null for direct-attach) |
| `display_order` | integer | No | Min 0 |
| `slots` | object | No | Slot configs keyed by slot number string |

#### Slot Schema

| Field | Type | Required | Constraints |
|-------|------|----------|-------------|
| `physical_slot_number` | integer | Yes | Min 0 |
| `physical_position` | object | No | `{row, col}` grid position |
| `label` | string | No | Custom display label |
| `role` | string | No | `wipe`, `os`, or `reserved` |
| `locked` | boolean | No | Prevents modification |
| `mappings` | object | No | Interface type mappings |

#### Slot Mapping Schema (per interface type)

| Field | Type | Required | Constraints |
|-------|------|----------|-------------|
| `slot_type` | string | Yes | `sas_expander`, `sas_direct`, `motherboard_sata`, `pcie_nvme` |
| `hardware_identifier` | string | Yes | Hardware path (e.g., `phy-0:0:0`, `ata3`, `101`) |
| `auto_detected` | boolean | No | Whether mapping was auto-detected |
| `pci_controller` | string | No | PCI address |
| `expander_sas_address` | string\|null | No | SAS expander WWN |

The `mappings` object supports two interface keys:
- `sas_sata`: Mapping for SAS or SATA drives
- `nvme`: Mapping for NVMe drives (used in hybrid slots)

## Traversal Presets

Traversal presets define how physical slots are numbered in the workbench display grid:

| Preset | Pattern | Typical Use |
|--------|---------|-------------|
| `top_left_down_then_across` | Number down each column, then move to the next column | Dell backplanes |
| `bottom_left_up_then_across` | Number up each column from bottom, then next column | Supermicro backplanes |
| `top_left_across_then_down` | Number across each row, then move down | Horizontal enclosures |
| `bottom_left_across_then_up` | Number across each row from bottom, then up | Bottom-up horizontal |

## Setup Instructions

### Step 1: Verify Hardware Detection

Before configuring enclosures, verify that the OS detects your HBA and expander hardware:

```bash
# List PCI devices (look for SAS/HBA controllers)
lspci | grep -i sas

# Check SAS expander detection
ls -la /sys/class/sas_phy/

# Check by-path entries
ls -la /dev/disk/by-path/

# For NVMe slots
ls -la /sys/bus/pci/slots/

# For SATA ports
ls -la /sys/class/ata_port/
```

### Step 2: Create a Template (if needed)

If your physical chassis doesn't match a built-in template:

1. Go to **System Administration** tab > **Layout Template Management**
2. Click **+ Create Template**
3. Fill in:
   - **Template ID**: Lowercase identifier (e.g., `supermicro_8bay`)
   - **Name**: Human-readable name
   - **Vendor**: Hardware vendor
   - **Bay Count**: Number of usable bays
   - **Rows** and **Cols**: Grid dimensions
   - **Traversal Preset**: Match your chassis numbering
   - **Hybrid Slots**: Comma-separated bay numbers that support NVMe (if any)
4. Click **Create Template**

You can preview the layout and animate the traversal order before saving.

### Step 3: Create an Enclosure

1. Go to **System Administration** tab > **Enclosure Management**
2. Click **+ Add Enclosure**
3. The enclosure wizard opens with two steps:

#### Step 3a: Configuration

- **Enclosure Name**: Enter a descriptive name (e.g., "Front Bay Array")
- **Display Order**: Enter a number for sort order (0 = first)
- **Select Physical Controller**: Choose the PCI controller that connects to this enclosure. The wizard shows:
  - Controller label (vendor/model if detected, otherwise PCI address)
  - Drive count (how many drives are currently detected on this controller)
  - Total slots (from hardware info)
  - Whether it uses a SAS expander (shows expander SAS address)
  - **Tip**: Insert a test drive into a bay and click "Refresh Drive Counts" to identify which controller corresponds to your physical enclosure
- **Layout Template**: Select the template that matches your chassis

#### Step 3b: Slot Assignment

- The wizard auto-maps slots from the master slot map (0→0, 1→1, etc.)
- Review the auto-detected mappings against actual drive presence
- Manually correct any incorrect mappings
- For hybrid templates, select the starting PCIe NVMe slot for auto-incrementing

### Step 4: Verify Mappings

After saving the enclosure:

1. Insert a known test drive into each bay
2. Check the Workbench tab to confirm each drive appears in the correct bay
3. Use the **Auto-Detect** button in the Interactive Bay Mapping section as a fallback
4. Verify via API:
   ```bash
   curl -sS http://127.0.0.1:5000/api/drives | jq '.[].bay'
   ```

### Step 5: Save Configuration

Click **Save Mapping Configuration** in the Interactive Bay Mapping section to persist all changes to `config/bay_map.json`.

## Hybrid NVMe Bay Configuration

Some enclosures support both SAS/SATA and NVMe drives in the same physical slot (hybrid bays). This is common with U.2/U.3 backplanes that accept either a SAS drive or an NVMe drive.

### How Hybrid Slots Work

1. **Template Configuration**: In the Template Management panel, specify which physical slots are hybrid using the `hybrid_slots` field (comma-separated bay numbers, e.g., "1,5,9").

2. **Enclosure Creation**: When creating an enclosure from a hybrid template, the wizard displays both SAS/SATA and NVMe mapping options for hybrid slots. You select a starting PCIe NVMe slot, and the system auto-increments PCIe slot numbers for sequential hybrid slots.

3. **Drive Detection**: During discovery, the system detects which interface type is present in each hybrid slot and updates the `auto_detected` flag for the active interface.

4. **UI Display**: Hybrid slots show the active interface type based on the detected drive.

### Example: 16-Bay Hybrid Enclosure

A 16-bay enclosure with slots 1, 5, 9, and 13 configured as hybrid:

| Slot | SAS/SATA Path | NVMe Path |
|------|--------------|-----------|
| 1 | SAS expander phy-0:0:1 | PCIe slot 101 |
| 5 | SAS expander phy-0:0:5 | PCIe slot 102 |
| 9 | SAS expander phy-0:0:9 | PCIe slot 103 |
| 13 | SAS expander phy-0:0:13 | PCIe slot 104 |

When an NVMe drive is inserted in slot 1, the system detects it at `/sys/bus/pci/slots/101` and maps it accordingly. When a SAS drive is inserted, the system detects it via the SAS expander phy path.

### NVMe Auto-Incrementing

When configuring a hybrid enclosure, select the starting PCIe NVMe slot number. The system automatically increments for each subsequent hybrid slot:

- Starting slot: `101`
- Hybrid slots 1, 5, 9, 13 → NVMe slots 101, 102, 103, 104

If the master slot map has no PCIe NVMe entries (e.g., no NVMe drives currently inserted), the wizard falls back to detecting unmapped NVMe drives via `/api/admin/unmapped-drives`.

## MPIO (Multipath I/O) Resolution

When a drive is dual-ported under MPIO (common with enterprise SAS drives), the system automatically resolves both paths to a single Device Mapper node.

### How It Works

1. During discovery, the system checks `/sys/block/<dev>/holders` for dm-* entries
2. If found, the device is mapped to `/dev/mapper/mpathX` or `/dev/dm-X` as the unified device path
3. A single device is presented to the UI and wipe operations

### udev Event Handling

When a dual-ported SAS drive is inserted:

1. The udev listener detects the `add` event for the raw device (e.g., `/dev/sdb`)
2. If the device is not already a dm-* or mapper/ device, the system waits 500ms for multipathd to bind
3. The device is re-resolved after the settling delay to get the final multipath parent
4. The resolved device is stored in runtime slot state and broadcast via WebSocket

### Verifying MPIO

```bash
# Check multipath status
multipath -ll

# Verify multipathd is running
systemctl status multipathd

# Check device holders
ls -la /sys/block/sdb/holders/
```

If MPIO resolution is not working:
- Verify `device-mapper-multipath` package is installed
- Check `/etc/multipath.conf` configuration
- Restart multipathd: `sudo systemctl restart multipathd`

## Multi-Enclosure Setups

Multiple enclosures can be configured independently with their own templates, controllers, and display order.

### Configuration

1. Create each enclosure separately using the enclosure wizard
2. Each enclosure must have:
   - A unique `id` (auto-generated from name)
   - A unique PCI controller (or a unique expander SAS address if sharing a controller)
   - A `display_order` value for UI sort order

### Collision Prevention

When two enclosures share the same HBA but connect to different SAS expanders, the system uses the `expander_sas_address` to distinguish slots. This prevents cross-expander slot collisions where slot 5 on expander A would incorrectly match slot 5 on expander B.

The device resolution code (`backend/device_resolution.py`) builds an exact by-path prefix that includes the expander SAS address:

```
pci-0000:af:00.0-sas-exp0x500056b3059bdcff-phy5-lun-0
```

This ensures slots on different expanders behind the same HBA never cross-match.

### Verifying Multi-Enclosure Setup

```bash
# Check that each enclosure has unique expander SAS address
curl -sS http://127.0.0.1:5000/api/admin/enclosures | jq '.enclosures[] | {id, pci_controller, expander_sas_address}'

# Verify no slot mapping conflicts
curl -sS http://127.0.0.1:5000/api/drives | jq '.[] | {bay, device, serial}'
```

## Auto-Detect Bays

The auto-detect feature (`POST /api/admin/auto-detect-bays`) scans hardware for physical backplane slots using two methods:

### Method A — SCSI Enclosure Services (SES)

Scans `/sys/class/enclosure` for slot-to-device mappings. This is the primary method for enclosures with SES support (most enterprise SAS backplanes).

For each slot in `/sys/class/enclosure/<enclosure_id>/slot_N/`:
1. Reads the `slot_number` file (or parses from slot ID)
2. Finds associated block device nodes under `device/block`
3. Maps the slot to its `/dev/disk/by-path/` entry
4. Creates or updates the bay map entry

### Method B — SAS Transport bay_identifier Fallback

Used when Method A finds no slots (passive direct-attach backplanes without SES).

For each `sd*` device in `/sys/block/`:
1. Walks up the sysfs parent tree to find `sas_device` directories
2. Reads the `bay_identifier` file from the SAS end device
3. Maps the bay number to the device's by-path entry

### When to Use Auto-Detect

- **Initial setup**: After installing the application on a new server
- **After hardware changes**: When adding or replacing HBA cards or expanders
- **Troubleshooting**: When drives appear in wrong bays or are not detected

Auto-detect preserves existing enclosure configurations and only updates bay-to-device-path mappings.

## Device Resolution

Once enclosures are configured, the system resolves active device paths from the persisted hardware identifiers in `config/bay_map.json`. No master slot map scan is needed for normal operation — the bay map is authoritative.

### Resolution by Slot Type

#### SAS Expander

Pattern: `pci-{pci_addr}-sas-exp{expander_id}-phy{phy_num}-lun-0`

When the expander SAS address is known, an exact prefix is built to prevent cross-expander collisions:

```python
exact_prefix = f"pci-{pci_controller}-sas-exp{expander_sas_address}-phy{physical_slot}-"
```

#### SAS Direct

Pattern: `pci-{pci_addr}-scsi-{host}:0:{slot}:0`

Matches by PCI controller and SCSI target ID.

#### Motherboard SATA

Pattern: `pci-{pci_addr}-ata-{ata_num}`

Matches by PCI controller and ATA port number.

#### PCIe NVMe

Two resolution methods:

1. **Slot folder matching**: Reads `/sys/bus/pci/slots/<hw_identifier>/address` to get the expected PCI address, then scans `/sys/class/block/nvme*` for a device whose PCI address matches.
2. **Direct by-path matching**: If the hardware identifier is a full by-path string (e.g., `pci-0000:18:00.0-nvme-1`), it resolves directly via `/dev/disk/by-path/`.

### Fallback: sysfs Resolution

If by-path resolution fails (symlinks removed by udev after SCSI bus reset), the system falls back to sysfs traversal using the persisted hardware identifier. The hardware identifier (e.g., `phy-0:0:0`, `ata1`) is stable and tied to the physical slot, so it works even after expander re-enumeration changes SCSI target IDs.

## Caching

### Master Slot Map Cache

- **TTL**: 3600 seconds (1 hour)
- **Invalidation**: Automatic on enclosure create/edit/delete, bay map save, auto-detect
- **Manual refresh**: `GET /api/admin/master-slot-map?force_refresh=true`

### SAS Expander Cache

- **TTL**: 3600 seconds (1 hour)
- **Per-PCI-address caching**: Results cached per controller
- **Invalidation**: Automatic on enclosure changes

### SCSI Projections Cache

- **TTL**: 3600 seconds (1 hour)
- **Invalidation**: Automatic on enclosure changes

### Drive Cache

- **Invalidation**: On bay map changes, auto-detect, udev hot-plug events, and drive removal
- Hardware topology caches (SAS expander, SCSI projections, master slot map) are NOT invalidated on drive hot-plug because drive hot-plug does not change physical hardware topology.

## Troubleshooting

### Drives Not Detected in Expected Slots

1. Verify enclosure configuration in System Administration panel
2. Check that PCI controller address matches actual hardware: `lspci | grep -i sas`
3. Confirm expander SAS address is correct for multi-expander setups
4. Inspect master map: `GET /api/admin/master-slot-map`
5. Verify slot type matches physical connection (SAS expander vs direct)
6. Check sysfs directly: `ls -la /sys/class/sas_phy/` for SAS phy paths
7. For NVMe: `ls -la /sys/bus/pci/slots/` to verify slot numbers

### Hybrid Slot NVMe Mapping Incorrect

1. Verify template has correct `hybrid_slots` array
2. Check starting PCIe NVMe slot selected during enclosure creation
3. Confirm `/sys/bus/pci/slots/` folder numbers match expected sequence
4. Re-create enclosure with correct starting NVMe slot number if needed

### Multipath Device Shows as Two Separate Drives

1. Check if drive is dual-ported SAS: `multipath -ll`
2. Verify `/sys/block/<dev>/holders` contains dm-* entries
3. Confirm MPIO resolution is working in discovery logs
4. Verify multipathd service is running: `systemctl status multipathd`
5. Restart multipathd: `sudo systemctl restart multipathd`

### Enclosure Creation Fails with Invalid Controller

1. Verify master map is populated: `GET /api/admin/master-slot-map`
2. Check that sysfs directories are accessible
3. Confirm HBA hardware is detected by OS
4. Rescan PCI bus: `echo 1 > /sys/bus/pci/rescan`
5. Check HBA driver is loaded: `lsmod | grep <driver_name>`

### Stale Drive Detection After Hot-Swap

1. The udev listener should automatically detect hot-swap events
2. If stale data persists, force master map refresh: `GET /api/admin/master-slot-map?force_refresh=true`
3. Wait for cache TTL to expire (1 hour for topology caches)
4. Re-seat drive and wait for kernel detection

### Multi-Enclosure Collision

1. Verify each enclosure has unique expander SAS address
2. Confirm PCI controllers are different for each enclosure (or expander addresses differ)
3. Check display order doesn't cause confusion
4. Re-configure enclosures with correct hardware bindings

## Case Studies

### Case Study 1: Dell R440 with SAS Expander (10-Bay)

**Hardware**: Dell R440 server with a Broadcom SAS 9305-24i HBA and a SAS expander backplane.

**Configuration**:
1. Created template `dell_r440_10bay` (2 rows, 5 cols, top-left-down-then-across)
2. Created enclosure `front_array` with PCI controller `0000:af:00.0` and expander SAS address `0x500056b3059bdcff`
3. Auto-mapped 10 slots (0-9) to phy-0:0:0 through phy-0:0:9
4. Inserted test drives and verified each appeared in the correct bay

**Result**: All 10 bays correctly mapped. Hot-swap events trigger udev listener and update the UI in real-time via WebSocket.

### Case Study 2: Supermicro with Hybrid Slots (16-Bay)

**Hardware**: Supermicro SC846 chassis with 16 bays, 4 of which are hybrid (support both SAS and NVMe U.2).

**Configuration**:
1. Created template `supermicro_16bay_hybrid` (4 rows, 4 cols, bottom-left-up-then-across, hybrid_slots: [1, 5, 9, 13])
2. Created enclosure `main_array` with PCI controller `0000:81:00.0` and expander SAS address `0x5003048023456789`
3. Auto-mapped SAS/SATA slots 0-15 to phy paths
4. Selected starting NVMe slot `101` for hybrid slots
5. System auto-incremented: slot 1→101, slot 5→102, slot 9→103, slot 13→104

**Result**: Both SAS and NVMe drives work in hybrid bays. The system detects the interface type based on which device appears at the mapped path.

### Case Study 3: Dual HBA Multi-Enclosure (2x 8-Bay)

**Hardware**: Server with two LSI SAS 9211-8i HBAs, each connected to a separate 8-bay direct-attach backplane (no expander).

**Configuration**:
1. Created template `generic_8bay` (2 rows, 4 cols, top-left-down-then-across)
2. Created enclosure `enclosure_a` with PCI controller `0000:04:00.0`, no expander (direct-attach)
3. Created enclosure `enclosure_b` with PCI controller `0000:82:00.0`, no expander (direct-attach)
4. Auto-mapped slots for each enclosure independently
5. Set display_order: enclosure_a=0, enclosure_b=1

**Result**: Two enclosures display in order. No slot collisions because each enclosure uses a different PCI controller. Drives in enclosure A resolve via `pci-0000:04:00.0-scsi-*` and drives in enclosure B resolve via `pci-0000:82:00.0-scsi-*`.
